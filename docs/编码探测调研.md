# 编码探测（ChardetDetector）调研

> 目的：搞清 `3rdparty/ChardetDetector` 在工程里干什么、影响面多大、替换成什么最稳。
> 结论来自仓库代码 + 本机实测（`tools/encoding-probe/`），没有引用外部文档。

## 1. 它在我们工程里干什么

调用链只有一条，长度三层：

```
libzip / minizip 后端
  └─ Common::trans2uft8(str, strCode)        src/archive/api/common.cpp:118
       └─ Common::detectEncode(data, fileName)  src/archive/api/common.cpp:145
            └─ Common::ChartDet_DetectingTextCoding()  → chardet 的 detect()
```

实际调用点（都是 ZIP 系归档的字符串字段）：

| 位置 | 用途 |
|---|---|
| `libzip_backend.cpp:83` | 归档注释 |
| `libzip_backend.cpp:95`、`:143` | 条目名 |
| `minizip_backend.cpp:55`、`:297`、`:324` | 条目名 |

也就是说：**影响面只有"ZIP 归档里非 UTF-8 编码的条目名和注释"**。tar/7z/rar 不经过它（那些格式自带编码标记或由外部命令输出 UTF-8）。

`detectEncode()` 拿到判定结果后并不直接用它解码，而是再走一层映射：

```cpp
if (结果含 "UTF-8" 或 "ASCII")          -> 用 UTF-8
else if (含 windows/IBM/x-mac/Big5/gb18030/iso) -> 用返回的编码名建 codec
else                                     -> textCodecDetect()   // 自带打分兜底
```

## 2. 旧实现是什么、有什么限制

- 是 Mozilla UniversalDetector（nsUniversalDetector + 各 `nsXXXProber`）的 C 封装，**7,065 行**（不含 `.tab` 频率表数据）。
- 本仓库这份编译时**没有定义 `CHARDET_BINARY_SAFE`**，只有 `detect(const char *, DetectObj **)`——**遇到 `NUL` 就截断**；`detect_r(data, len)` 这个二进制安全版本不存在。
- 返回的编码名是它自己的写法：`gb18030`（小写）、`Big5`、`Shift_JIS`、`EUC-KR`、`ASCII`。
- 下游 `trans2uft8()` 用**字符串匹配**消费这些名字：`"gb18030" == strCode` 是大小写敏感的精确比较，`contains("Big5", CaseInsensitive)` 则宽松。**换探测库时这个名字写法是最容易踩的地方。**

## 3. 实测：旧实现 vs uchardet vs ICU

探针在 `tools/encoding-probe/`（`./run_probe.sh [构建目录]`），同一份字节三边各判一次。

完整样本（一段完整中文/日文/韩文）：

| 样本 | 旧 chardet | uchardet | ICU |
|---|---|---|---|
| GBK | `gb18030` 0.99 | `GB18030` | `GB18030` 100 |
| Big5 | `Big5` 0.99 | `BIG5` | `Big5` 88 |
| Shift_JIS | `Shift_JIS` 0.99 | `SHIFT_JIS` | `Shift_JIS` 100 |
| EUC-KR | `EUC-KR` 0.99 | `UHC` | `EUC-KR` 100 |
| ASCII | `ASCII` 1.00 | `ASCII` | `ISO-8859-1` 42 |
| UTF-8 | `UTF-8` 0.99 | `UTF-8` | `UTF-8` 100 |

短样本（**这就是条目名的真实形态**，几个字节）：

| 样本 | 旧 chardet | uchardet | ICU |
|---|---|---|---|
| `中文.txt`(GBK) | `gb18030` 0.99 | `KOI8-R` ❌ | `UTF-16BE` ❌ |
| `報告.txt`(Big5) | `Big5` 0.99 | `IBM852` ❌ | `ISO-8859-1` ❌ |
| `資料/ファイル.txt`(SJIS) | `Shift_JIS` 0.67 | 空 ❌ | `UTF-16BE` ❌ |

短样本 + 中文填充（`为增加探测率保留的中文` 之类）：

| 样本 | 旧 chardet | uchardet | ICU |
|---|---|---|---|
| GBK 短名 + 填充 | `gb18030` 0.99 | `GB18030` ✅ | `GB18030` 100 ✅ |
| Big5 短名 + 填充 | `Big5` 0.99 | `BIG5` ✅ | `Big5` 100 ✅ |

**这是本次调研最关键的一条**：直接换成 uchardet / ICU，在"条目名"这个真实场景上会**退化**；必须先给短输入补足上下文（旧代码里已经有类似的填充动作，但只在输入已经是 UTF-8 中文时触发，对 GBK 字节不触发）。

UTF-16 三家都判不出来（旧实现返回空 → `trans2uft8` 原样返回字节；uchardet/ICU 会误报成 windows-1252）。这项三家都不做，不在替换目标内。

## 4. 三个方案

| 方案 | 依赖 | 优点 | 代价/风险 |
|---|---|---|---|
| **A. uchardet** | 系统已有 `uchardet 0.0.8`，MIT | 依赖最小（几百 KB）、同样是统计探测、C API 简单 | 无置信度接口；短样本必须补填充；编码名写法不同（`GB18030`/`BIG5`/`UHC`）要做归一化 |
| B. ICU `ucsdet` | 系统已有 ICU 74.2 | 有置信度、编码覆盖最全、维护活跃 | 引入 `icu-i18n` 依赖（库体积几十 MB），对一个只判条目名的场景偏重；名字写法同样要归一化 |
| C. 自研最小探测器 | 无 | 完全可控，只覆盖我们真正需要的几种 | 频率表 + 状态机约 400–600 行；准确率要自己调，短名场景风险最高；本质是把 7 千行里的 CJK 部分重写一遍 |

旧的 7,065 行里，**大部分与我们无关**：单字节编码（ISO-8859-x、windows-125x、KOI8、IBM866）、希伯来、泰文、EUC-TW 这些 prober 对中文用户的 ZIP 名字基本用不上，真正起作用的是 `nsMBCSGroupProber` 里的 GB2312/Big5/SJIS/EUC-JP/EUC-KR + `nsUTF8Prober`。

## 5. 推荐

**方案 A：uchardet + 两层适配**，改动集中在 `Common::detectEncode()`：

1. **填充**：输入短于 ~64 字节且含非 ASCII 时，按"疑似编码"补一段同编码样例（或统一补一段中文填充），把短样本拉长到可判定长度；
2. **名字归一化**：加一张小映射表，把 `GB18030/GBK → gb18030`、`BIG5 → Big5`、`SHIFT_JIS → Shift_JIS`、`UHC/EUC-KR → EUC-KR`、`ASCII → UTF-8` 收敛到旧实现的写法，保证 `trans2uft8()` 的判断分支不用改。

这样 `trans2uft8()` 和所有后端的调用代码都不动，替换面只有 `detectEncode()` 内部 + CMake 依赖。

## 6. 验收方式（可复用现有工装）

1. **语料**：用 Python 以 raw bytes 写三份 zip（条目名分别为 GBK/Big5/Shift_JIS 编码，且不带 UTF-8 标志位），例如 `name_gbk.zip` / `name_big5.zip` / `name_sjis.zip`；
2. **基线**：`dc-off`（旧 chardet）`record` 出 `*.archiveData.entries[*].strFileName`；
3. **验证**：自有实现 `verify`，要求解出来的名字逐字节一致；
4. 另加一条"短名 + 长名混合"的样本，防止只在长样本上成立。

## 7. 不做的事

- 不支持 UTF-16/UTF-32 条目名（三家都不支持，旧实现同样不支持）；
- 不追求单字节编码（Latin-1/西里尔/泰文）的判定精度——这类名字现在的实现也只是"能用"，替换后保持同等水平即可；
- 不改 `trans2uft8()` 的分支结构（那是契约层对外行为）。

## 8. 全局排查清单（保留决策依据）

### 8.1 调用面：一个入口，两个消费点

| 位置 | 作用 |
|---|---|
| `src/archive/api/common.cpp:121` | `trans2uft8()` 里唯一一次 `detectEncode(str)` 调用 |
| `src/archive/api/common.cpp:145` | `detectEncode()`：调用 chardet + 把结果映射成 `GBK` / `UTF-8` / 原名 |
| `src/archive/api/common.cpp:182` | `ChartDet_DetectingTextCoding()`：`detect_obj_init` → `detect` → `detect_obj_free` |
| `libzip_backend.cpp:83` | 归档注释 |
| `libzip_backend.cpp:95`、`:143` | 条目名（列表、单条重命名） |
| `minizip_backend.cpp:55`、`:297`、`:324` | 条目名 |
| `3rdparty/libzipplugin.cpp:107`、`:744` | 旧实现同两点（只影响 `dc-off` 对照构建） |

**不进 chardet 的路径**：tar / 7z / rar 后端；以及**所有写路径**——`libzip_write.cpp` 一律用
`ZIP_FL_ENC_UTF_8` 写入，所以探测结果只影响"读出来的名字"，不影响写进去的名字。

### 8.2 构建面

| 位置 | 依赖方式 |
|---|---|
| `src/archive/api/CMakeLists.txt:75` | 静态库 `compressor-ChardetDetector` 链进 `compressor-interface` |
| `3rdparty/interface/CMakeLists.txt:69` | 旧契约层（`dc-off`）同样链接 |
| `tests/UnitTest/.../CMakeLists.txt` | 单元测试链接 |
| `tests/FuzzyTest/libfuzzer/` | 直接把它的 `.cpp` 编进 libFuzzer 目标（工装存在，默认不跑） |
| `3rdparty/clizipplugin/CMakeLists.txt:21` | 引用其头文件，但该目录**未参与构建**（`3rdparty/CMakeLists.txt:88` 注释为"不可用"） |

### 8.3 行为面（容易忽略的三点）

1. **只有 `detect()`**：本仓库这份没开 `CHARDET_BINARY_SAFE`，无 `detect_r()`，遇 `NUL` 截断。
2. **置信度是死变量**：`detectEncode()` 里 `chardetconfidence` 只被赋值，从未参与任何阈值判断。
3. **单元测试是空壳**：`test_detectEncode`、`test_ChartDet_DetectingTextCoding`、`test_textCodecDetect`
   三个 `TEST_F` 函数体都是空的，实际没有覆盖。

### 8.4 结论

它是**叶子依赖**：唯一出口是"ZIP 条目名/注释的解码"，写路径完全不经过它，也没有任何第三方代码反向依赖它的符号。
保留的代价是 `3rdparty/` 里留着这 **7,065 行**；风险是"处理不可信输入的老 C++ 代码"，已用 ASan+UBSan
跑 2 万轮随机输入（`tools/encoding-probe/fuzz.cpp`）无崩溃。

## 9. 最小验证：自研状态机 + 沿用频率表

代码：`tools/encoding-probe/own_detector.{h,cpp}`（约 330 行），与旧实现同表同公式：

- **状态机自己写**：GBK/GB18030（含四字节形式）、Big5、Shift_JIS（含半角片假名单字节）、EUC-KR 的合法字节范围；
- **频率表沿用** Mozilla 的 `.tab`（表里自带 `TYPICAL_DISTRIBUTION_RATIO` 与 `TABLE_SIZE`）；
- **打分公式与阈值照公开实现**：`freq / ((total - freq) * ratio)`，封顶 0.99，判定下限 0.20。

### 9.1 与旧实现的对拍

差分测试：按 GBK / Big5 / Shift_JIS / EUC-KR 四种编码各生成 60 个随机文件名（2–12 个汉字，带常见后缀），
共 240 个样本，逐条比对"判定编码 + 置信度"：

| 结果 | 数量 | 占比 |
|---|---:|---:|
| 判定一致 | 231 | 96.3% |
| 不一致 | 9 | 3.7% |

9 条分歧逐条查过（都是 **4–16 字节的极短名字**）：

| 样本 | 真实编码 | 旧 chardet | 自研 | 谁对 |
|---|---|---|---|---|
| `索據例編.zip` | Big5 | `windows-1252` 0.50 | `Big5` 0.44 | **自研** |
| `码源试演.txt` | GBK | `KOI8-R` 0.54 | `gb18030` 0.37 | **自研** |
| `演频数.pdf` | GBK | `TIS-620` 0.65 | `gb18030` 0.56 | **自研** |
| `录单例指署汇.pdf` | GBK | `windows-1251` 0.56 | `gb18030` 0.56 | **自研** |
| `考票.pdf`(8B) | GBK | `windows-1252` | 判不出 | 都不对 |
| `冊版`(4B) | Big5 | `windows-1252` | 判不出 | 都不对 |
| `通要志.zip`(10B) | GBK | `gb18030` | `UTF-8` | 真歧义（字节同时是合法 UTF-8） |
| `片同志片.zip`(12B) | GBK | `gb18030` | `UTF-8` | 真歧义 |

结论：分歧集中在两类——**旧实现的单字节回落**（旧有 SBCS 探测组，自研没有，短名时它会用 `windows-1252` 之类"兜底"），
以及**极短样本的编码歧义**（同一串字节既是合法 GBK 又是合法 UTF-8）。**四分之三的分歧里自研判定更接近真实编码。**

### 9.2 要做到 100% 等价还差什么

| 缺口 | 需要补的 |
|---|---|
| 单字节回落 | 照旧实现补 SBCS 探测组（534 行），或至少补一条"无 CJK 命中时回落 windows-1252"的规则 |
| UTF-8 判定时机 | 旧实现的 UTF-8 prober 有最小数据量与状态机严格度，需要逐条对齐 |
| 组间竞争 | 旧实现按 ESC→UTF-8→MBCS→SBCS 的顺序竞争，需要复刻顺序与短路（0.95）行为 |

### 9.3 判断

- "自研状态机 + 沿用频率表"这条路**成立**：96% 一致，且分歧处多为自研更准；
- 要 100% 等价，不是算法问题而是"补齐回落与竞争顺序"的工程问题，估计再加 2–3 天；
- 如果只要求"中文/日文/韩文 ZIP 名判得对"，当前版本已经够用，剩余分歧都在 4–16 字节的歧义样本上。

## 10. 完整移植进度（目标：与外文场景也 100% 等价）

做法调整：不做"只覆盖 CJK"的简化版，而是**算法自己写、参数全部对齐**，逐组推进。
参数（状态机表、频率表、语言模型、上下文表）由 `tools/encoding-probe/gen_tables.py`
从旧实现的源文件机械抽取到 `own_tables.h`，只做 `own_` 前缀重命名，不含任何函数体。

| 阶段 | 内容 | 状态 |
|---|---|---|
| 1 | BOM 识别、纯 ASCII 判定、MBCS 组（UTF-8 / SJIS / EUC-JP / gb18030 / EUC-KR / Big5 / EUC-TW）+ 日文上下文分析 + 组内竞争 | ✅ 完成 |
| 2 | SBCS 组：`FilterWithoutEnglishLetters` + 14 个单字节语言模型 + 希伯来（logical/visual） | ✅ 完成 |
| 3 | Latin1 prober（类表 + 英文过滤） | ✅ 完成 |
| 4 | ISO-2022 Esc prober（JP/CN/KR/HZ 四个状态机） | ✅ 完成 |

### 阶段 1 的差分结果（240 个随机文件名）

| 版本 | 一致率 |
|---|---|
| 手写状态机（简化版，阶段 0） | 231 / 240 |
| MBCS 全量移植（阶段 1） | **233 / 240** |

剩下 7 条全部是**旧实现由单字节组给出答案**的样本（`windows-1252` / `KOI8-R` / `TIS-620` / `windows-1251`），
即分歧 100% 落在阶段 2、3 尚未移植的部分，MBCS 组本身在这批样本上已无差异。

移植过程中确认的两个关键参数错位（都会导致判定翻转）：
1. `gb18030` 探测器用的是 **`GB18030SMModel`**（四字节能力），不是 `GB2312SMModel`；
2. 日文上下文序号的 `GetOrder` **只对平假名行**返回 0–82（SJIS `0x82 0x9F..0xF1`、EUC-JP `0xA4 0xA1..0xF3`），其余返回 -1。

### 最终验收（1,169 个样本，名字 + 置信度逐位对比）

| 语料 | 规模 | 结果 |
|---|---|---|
| 基础语料（GBK/Big5/SJIS/EUC-KR 文件名） | 240 | **240 / 240 完全一致** |
| 扩语料（23 种编码 × 40 + 10 个边界样本：11 种单字节、UTF-16 LE/BE、ISO-2022 JP/KR、HZ、空/单字节/NUL/纯高位） | 929 | **929 / 929 完全一致** |

"完全一致"指编码名与置信度（两位小数）都相同。

### 移植过程中发现的 6 个隐藏参数（每一个都会导致判定翻转）

1. `gb18030` 探测器用的是 `GB18030SMModel`（四字节能力），不是 `GB2312SMModel`；
2. 日文上下文 `GetOrder` **只对平假名行**返回 0–82（SJIS `0x82 0x9F..0xF1`、EUC-JP `0xA4 0xA1..0xF3`）；
3. **MBCS 组会先按"含高位字节的片段"切分**再喂给各探测器，纯 ASCII 段跳过，且片段边界跨调用保持（`mKeepNext`）——一次性喂整块会让结果不同；
4. Latin1 prober 的 `Reset()` 把 `mLastCharClass` 初始化为 `OTH(=1)`，不是 0；
5. 希伯来判定器（13 号）**也是 active 的**，它不产置信度但必须被喂数据，否则词尾字母打分会一直为 0，`windows-1255` 与 `ISO-8859-8` 就分不开；
6. 两个过滤器的语义：`FilterWithoutEnglishLetters` 返回空则整组跳过；`FilterWithEnglishLetters` **成功就只用过滤结果**（即使为空），失败才回退原缓冲。
7. **空输入返回 `ASCII 1.0`**：旧实现里 `mInputState` 默认 `ePureAscii`，`HandleData` 的 `switch` 落到 default 分支就会置 ASCII，即使一个字节都没喂进去。我原先返回"判不出"，是错的。
8. **Esc 状态下不走"三组取最高"**：命中 ESC 但 Esc prober 没定案时，旧实现直接 `break`，`DataEnd` 里也只处理 Highbyte 分支。我原先继续走三组比较，还对未初始化的组取名字，直接抛异常。

### 10.1 随机字节差分（进程内，1 亿字节量级）

`tools/encoding-probe/diff_fuzz.cpp`：同一份字节同时喂给旧 `detect()` 与 `encdet::detect()`，
比对编码名与置信度。语料 = 11 万条随机短串（1–64 字节）+ 2.2 万条随机长串（1–3 KB，用来压 1024 门槛与短路路径）。

| 轮次 | 样本数 | 名字不一致 | 置信度不一致 |
|---|---:|---:|---:|
| 20,000 | 22,000 | 0 | 0 |
| 120,000 | **132,000** | **0** | **0** |

这两条隐藏行为（空输入、Esc 状态）就是这么发现的——固定语料和真实文件名都碰不到它们。

## 11. 整包探测（已采用）

同一归档的所有条目名先拼接，探测一次，再用这个编码统一解码。

三处改动缺一不可：

| # | 改动 | 位置 |
|---|---|---|
| 1 | 全包原始名字拼接后探测一次；条目名本身是合法 UTF-8 的仍按 UTF-8 | `libzip_backend.cpp`、`minizip_backend.cpp` |
| 2 | `trans2uft8()` 按探测结果直接取 codec（旧逻辑把 Big5/windows-*/ISO-*/x-mac-* 一律当 GBK 解） | `common.cpp` |
| 3 | 探测前不"补中文"（填充串是 UTF-8，拼到 GBK/Big5 字节上会污染统计，会让整包探测返回空） | `common.cpp::detectEncode` |

实测（180 个包 × 6 个名字 = 1,080 个名字，编码已知）：

| 模式 | 名字正确率 | 整包全对 |
|---|---|---|
| `per-entry`（旧行为） | 466/1080 = 43.1% | 49/180 |
| 默认（整包探测） | 943/1080 = **87.3%** | **150/180** |

剩余错包全部是西里尔/泰文同族单字节混淆（cp1251 → x-mac-cyrillic、windows-1255；tis620 → KOI8-R、ISO-8859-5），
这些包**旧 chardet 判得一样错**（1,260 个样本新旧输出逐位相同），属三方库固有歧义，不再优化。

基线：`goldens/` 是当前基线（57/57）。旧版行为需要对照时，用 `USE_OWN_ARCHIVE=OFF` 构建
`3rdparty` 版本做黑盒对比，代码里不再保留切换开关。
