# 后端自研替换：实施计划 (v3)

## 0. 目标（按这个模型写）

`src` 现在依赖 `3rdparty/` 里的代码：

```
src/（业务） ──include──► 3rdparty/interface/（契约：archiveinterface.h、commonstruct.h、datamanager.h、queries.h、kpluginmetadata.h）
             ──运行时加载► 3rdparty/<后端>/*.so（10 个插件）
```

**我们要做的事：在 `src/` 下新增一套我们自己的等价实现，让 `src` 改为依赖它；`3rdparty/` 保持原样不动，作为对照（标准答案），全部等价验证通过后再整体删除。**

```
src/（业务，不改）
    ├─ 依赖 ──► src/archive/api/          ← 我们自己写的契约（与 3rdparty 的逐字同名）
    └─ 依赖 ──► src/archive/backends/     ← 我们自己写的后端实现
                 src/archive/plugins/     ← 注册壳（.so 名、元数据不变）

3rdparty/  ← 一行不动，只在最后一步整体删除
```

三条约束：

| # | 约束 | 原因 |
|---|---|---|
| 1 | **`src` 业务代码不改** | include 的名字、调用方式、`DataManager` 读法都不变；只改构建配置里的源码目录 |
| 2 | **`3rdparty/` 一行不改** | 它是"标准答案"。改了它，就等于同时改了考题和答案，等价性无从谈起 |
| 3 | **一次换一个后端，可回退** | 每个后端一个 CMake 开关，OFF 就是旧实现，一行配置回退 |

## 2. 在 `src` 下建什么

```
src/archive/
    api/            契约（自有版权）：与 3rdparty 的契约头逐字同名同签名
                    archiveinterface.{h,cpp}  commonstruct.h  datamanager.{h,cpp}
                    queries.{h,cpp}  common.{h,cpp}  ddlog.h  kcoreaddons_export.h
                    kpluginmetadata.{h,cpp}  kpluginloader.{h,cpp}  kpluginfactory.{h,cpp}
    backends/       实现
                    singlefile/  libarchive/  libzip/  cli/  encoding/
    platform/       进程（QProcess + 需要的 forkpty）、路径守卫、原子替换
    plugins/        注册壳：每个后端 ~100 行，含原样复制的 kerfuffle_*.json
```

**为什么 `api/` 要逐字同名**：`src` 里的 `#include "archiveinterface.h"`、`DataManager::get_instance()`、`FileEntry` 字段名，一个都不能变。同名 + 同签名，业务代码才能零改动。

**为什么 `plugins/` 也要有**：`PluginManager` 扫的是 `/usr/lib/deepin-compressor/plugins/*.so`，靠 `.so` 文件名 + 内嵌 JSON 元数据（`Id`/`Name`/优先级/mime）。壳只是入口，实现在 `backends/`。

## 3. 怎么切换（核心机制）

**同名构建目标 + 源码目录二选一。** 不改 `3rdparty`，只改 CMake 编译谁。

```cmake
# 每个后端一个开关，默认 OFF = 继续用 3rdparty
option(OWN_SINGLEFILE "build our own single-file backend" OFF)
option(OWN_TAR        "build our own tar/libarchive backend" OFF)
option(OWN_ZIP        "build our own zip backend" OFF)
option(OWN_CLI        "build our own 7z/rar/pigz backends" OFF)
option(OWN_ENCODING   "build our own encoding detector" OFF)
option(OWN_API        "build our own contract layer" OFF)

# 目标名不变，只有源码路径变
if (OWN_SINGLEFILE)
    set(GZ_SRC  ${CMAKE_SOURCE_DIR}/src/archive/plugins/gz/gz_plugin.cpp
                ${CMAKE_SOURCE_DIR}/src/archive/backends/singlefile/gz_backend.cpp ...)
else()
    set(GZ_SRC  ${CMAKE_SOURCE_DIR}/3rdparty/libsinglefileplugin/gzplugin/gzplugin.cpp ...)
endif()
add_library(gzplugin SHARED ${GZ_SRC})        # 名字不变 → 安装路径、PluginManager 都不用改
```

必须同时满足的四条（少一条就加载不到 / 编不过）：

| 约束 | 说明 |
|---|---|
| 目标名不变 | `gzplugin` `libzipplugin` `readwritelibarchiveplugin` …（根 `CMakeLists.txt` 的 `install(TARGETS …)` 与测试工程都按名字引用） |
| `.so` 文件名与安装路径不变 | 仍是 `${CMAKE_INSTALL_LIBDIR}/deepin-compressor/plugins` |
| `kerfuffle_*.json` 内容不变 | `Id`/`Name`/优先级/mime 是业务选型依据（`uitools.cpp` 用 `name().contains(...)`） |
| 两份契约不能同时链接 | 同名类会符号重复 → `OWN_API` 是**互斥开关**：ON 编 `src/archive/api`，OFF 编 `3rdparty/interface`，都产出 `compressor-interface` |
| include 解析 | `src/archive/api` 与 `3rdparty/interface` 都进 include 路径时按开关二选一，保证 `#include "archiveinterface.h"` 不歧义 |

## 4. 测试：golden 是两边的裁判

同一套用例，对"旧 `.so`"和"新 `.so`"各跑一遍，比同一份基线。

```bash
# 旧实现（3rdparty）
conformance --backend gz --so build/3rdparty/libsinglefileplugin/gzplugin/libgzplugin.so --op extract --sample x.tar.gz
# 新实现（src）
conformance --backend gz --so build/src/archive/plugins/gz/libgzplugin.so --op extract --sample x.tar.gz
```

比什么（"功能一致"的定义）：

| 类别 | 字段 |
|---|---|
| 返回值 | `finish`、`errorType()`、`async`、`waitTimedOut` |
| 列表数据 | `qSize`、`compressedSize`、`comment`、`isListEncrypted`、每条 `name/fullPath/isDir/size/mtime/alias/index`、首层条目 |
| 信号 | 进度序列（含单调性）、当前文件名、完成/取消、**Query 序列**（类型+应答） |
| 落盘 | 每文件 sha256、权限、mtime、软链相对目标 |
| 产物 | 由 `bsdtar -tf` 独立列出（不让被测后端验证自己） |

基线由**旧实现**录制（已录 16 个用例，16/16 通过），之后任何实现都与之比对。用例级可声明不稳定字段（如 `gz.extract` 的 mtime——实测单文件插件不恢复），必须逐用例声明。

### 每一步的验收（都一样，只是范围不同）

1. 开关 **OFF**：基线 `verify` 全绿（证明旧实现没被误伤）；
2. 开关 **ON**：同一批用例全绿（证明新实现等价）；
3. 两个 `.so` 同时存在时做一次 `run_matrix.py diff`，差异逐条登记（要么修实现，要么是旧实现的历史怪癖，评审后更新基线）；
4. `git diff` 里 `src/` 的**业务**文件为空（只允许新增 `src/archive/`）。

### 第 1 步为什么单独做（api/）

`src` 现在 include 的是 `3rdparty/interface` 的头。要让 `src` 改依赖我们的契约，必须有一份同名的头，并且**和旧的不能同时进 include 路径**（同名类会符号重复）。

做法：`OWN_API=ON` 时，`compressor-interface` 由 `src/archive/api/` 编译，include 路径只加 `src/archive/api`；OFF 时保持现状。头的内容先"逐字复制"（保证零行为差异），等所有后端换完，再在最后一步做收敛（删掉 `src` 没用到的 `enum Plugintype`、`m_ePlugintype`、`isUserCancel`，`KPluginMetaData` 换成自有薄实现）。这样"契约收敛"和"后端替换"不会互相干扰。

### 第 7 步收尾

- 全量开关 ON 跑一遍 40 个用例 + 883 个业务 UT，全绿；
- 删 `3rdparty/` 整个目录、`add_subdirectory(3rdparty)`；
- `debian/control` 去掉 `libkf6codecs-dev`、`libkf6archive-dev`（`libzip`/`minizip` 取决于是否做附录 B）；
- 自研率复核 + 出报告。

## 7. 决策项

`Query` 的密码存在 `m_data["password"]`（由对话框写入），外部只能调 `setResponse()` 表达"确定/取消"，所以**加密包成功解压无法自动化**。建议在 `src/archive/api/queries.h`（第 1 步之后就是我们自己的文件）新增一个函数，不动已有签名：

```cpp
void setQueryData(const QString &key, const QVariant &value);   // 供自动化测试注入响应
```

不批的话，"加密包"用例只能覆盖取消路径，密码正确路径永远手工测。

## 12. 插件框架（KPlugin*）替换现状

`3rdparty/interface/plugin/` 共 1,981 行，`src` 只有两处在用：
`pluginmanager.cpp` 的 `findPlugins()` 和 `uitools.cpp` 的 `factory()->create<T>()`。
自有实现放在 `src/archive/api/plugin/`，类名与方法签名保持一致，`src/source/` 零改动。

| 旧文件 | 自有实现 | 行数 |
|---|---|---:|

| `kpluginloader.h/.cpp`（440+312） | `plugin/kpluginloader.h/.cpp` | 51 + 127 |

## 13. 进程框架（KProcess / KPTY）移除

`3rdparty/interface/process/` 共 1,746 行。ON 构建里已经完全不再编译，`PENDING_SOURCES` 清空。
前提是三处依赖都已经处理掉：

| 依赖方 | 处理方式 |
|---|---|
| `src/source/common/processopenthread.cpp` | `KProcess` → `QProcess`，输出改走 `nullDevice()` 防止管道写满 |
| `3rdparty/cli7zplugin`、`3rdparty/clirarplugin` | 已由自有 `CliRunner` 取代（`fork/exec` + pty） |
| `3rdparty/clipzipplugin` | 移入 `src/archive/plugins/clipzip`，`KPtyProcess` → `QProcess` |

`clipzip` 的 pty 没有实际作用：`pzip` 通过临时文件收密码，源码里没有 `getpass`/`isatty`，
`setPtyChannels(StdinChannel)` 只是照抄 KDE Ark 的写法，去掉后行为不变。

### zip 的实际后端选择（`src/source/common/uitools.cpp`）

| 场景 | 排除规则 | 命中的后端 |
|---|---|---|
| 读 / 解压 zip（`bWrite=false`） | `remove7zFlag` 跳过 7z、`removePzipFlag` 跳过 pzip | **libzip** |
| 压缩 zip（`bWrite=true`） | 无 | 按优先级 **clipzip(200) → pzip** |
| zip 追加（`APT_AutoWithoutPzip`） | 跳过 pzip | cli7z |

也就是说 `clipzipplugin` 只走压缩路径，`extractFiles()`（依赖 `punzip`）在产品里不会被调用；
`punzip` 未参与构建不影响解压。clipzip 的等价性只需覆盖 `add`。

### 验证

| 项 | 结果 |
|---|---|
| 读用例 | 51/51 |
| 写操作语义 | 54/54（新增 `clipzip.add` 4 项） |
| `libcompressor-interface.so` 里的 KPty 未定义符号 | 0 |

### 已知未覆盖

| 场景 | 原因 |
|---|---|
| `clipzip` 解压 | 不在生产路径上（读 zip 时被 `removePzipFlag` 跳过，固定走 libzip），无需验证 |
| `clipzip` 列表 | `list()` 是桩函数，直接返回 `PFT_Error`（注释写"pzip 目前不支持列表功能"），旧实现即如此 |

## 14. 编码探测替换（ChardetDetector → 自有实现）

### 位置

| 之前 | 现在 |
|---|---|
| `3rdparty/ChardetDetector`（7,065 行 C++ + 254 KB 频率表），`Common::ChartDet_DetectingTextCoding()` 直接调它的 `detect()` | `src/archive/api/encoding/`：`encoding_detector.{h,cpp}`（约 900 行算法）+ `encoding_tables.h`（约 5,200 行纯数据，脚本生成） |

`Common::ChartDet_DetectingTextCoding()` 的签名和调用点不变，`detectEncode()` / `trans2uft8()` 一行没改。

### 做法

- **算法自己写**：状态机驱动、分布打分、日文上下文分析、SBCS/Latin1/Esc 组、组间竞争、阈值；
- **参数对齐**：状态机表、14 个单字节语言模型、拉丁表、日文上下文表、5 张频率表，全部由
  `tools/encoding-probe/gen_tables.py` 从旧实现机械抽取（只做 `own_` 重命名与 `static` 化，不含函数体）。

### 等价性验证

| 验证项 | 规模 | 结果 |
|---|---|---|
| 探测器级差分（编码名 + 置信度逐位对比） | 1,169 个样本（23 种编码 × 40 + 边界样本 + 基础语料） | **100% 一致** |
| 端到端：非 UTF-8 条目名 zip（GBK/Big5/SJIS 原始字节，无 UTF-8 标志） | 新增 3 条用例 | **3/3 通过**（含旧实现把 Big5 名误判成 gb18030 的那条，逐字节一致） |
| 既有读用例 | 54 条 | **54/54** |
| 写操作语义 | 54 项 | **54/54** |

### 构建变化

`OWN_API=ON` 时不再 `add_subdirectory(ChardetDetector)`，该静态库彻底不出现在 ON 构建里；
`3rdparty/ChardetDetector` 仅由 `dc-off`（全旧实现对照构建）使用。

### 移植中踩到的 6 个隐藏参数

见 `docs/编码探测调研.md` §10 末尾（gb18030 用四字节状态机、MBCS 组按高位片段切分、Latin1 初值 `OTH`、
希伯来判定器必须参与、日文上下文只认平假名行、两个过滤器的空结果语义）。
